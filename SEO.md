# SEO Implementation (Phase 20)

## What's dynamic vs. static

Every page renders a `<Seo>` (`src/components/Shared/Seo.jsx`) or relies on
the site-wide `<GlobalSeo>` (`src/components/Shared/GlobalSeo.jsx`, mounted
once in `App.jsx`) for title, meta description, canonical URL, Open Graph,
Twitter card, and JSON-LD. Product pages compute all of this from the
actual fetched product — nothing is hardcoded per-product.

## No fabricated data

Per the task constraint, none of this implementation invents:
- **Reviews/ratings** — Product JSON-LD (`src/seo/structuredData.js`) has
  no `aggregateRating`/`review` fields at all. This app has no real review
  data anywhere; adding a rating snippet would be misinformation search
  engines index and act on.
- **Prices/availability** — Product JSON-LD's `offers.price` and
  `offers.availability` are read directly from the product object the page
  actually fetched (real price, real `getStockInfo` result). If a product
  has no valid numeric price, the `offers` block is omitted entirely rather
  than defaulted to 0.
- **Business info** — `src/seo/siteConfig.js` documents exactly which
  fields (logo URL, social handles, business address) have no verified
  source in this codebase and are left `null`/omitted rather than filled
  with placeholder text. Fill them in with real values when you have them;
  don't put example.com-style placeholders into production metadata.

## Clean product URLs

Route changed from `/product/:id` to `/product/:id/:slug?`
(`src/routes/AppRoutes.jsx`). The `:slug` segment is decorative only —
`ProductDetailPage` fetches by `:id` alone, exactly as before, so:
- Existing `/product/:id` links (bookmarks, shared links, anything the
  backend or emails already reference) keep working unchanged.
- A stale or mismatched slug never 404s; the page still renders correctly,
  and its `<link rel="canonical">` points at the *current*, correctly
  slugified URL — so search engines converge on one canonical form even if
  a product's name (and therefore its slug) changes later.

This is the most that's achievable without a backend change — the backend
has no `slug` field (see `src/services/productsService.js`), only `id`.
A backend-issued, stable slug field would be a stronger long-term choice,
but is out of scope for a frontend-only change.

## Canonical / indexability rules

- **Product pages**: always indexable, canonical = clean slug URL.
- **Home**: always indexable, canonical = `/`.
- **Product listing (`/products`)**: indexable only for the base page or a
  single-category filter (`?category=X`) — a real, meaningful, stable
  destination. Any other filter combination (price range, in-stock toggle,
  sort, pagination, or multiple categories at once) is `noindex` and
  canonicalizes back to the clean base/category URL, since those
  combinations produce unbounded near-duplicate content that isn't worth a
  search engine's crawl budget.
- **Search results (`/search`)**: always `noindex, follow` — query-driven,
  unbounded, and largely duplicates what `/products` and product pages
  already cover. `follow` still lets crawlers reach product links from
  here.
- **Account/cart/checkout/orders/wishlist/addresses/OTP/order-success**:
  always `noindex` — private or transient per-user state, never a useful
  search landing page.
- **404**: `noindex`. Note: this is a client-side route match inside a
  single-page app, so the server still returns HTTP 200 for the URL, not a
  real 404 status. Fixing the actual status code needs a server/hosting
  config change (e.g. a catch-all rewrite that still sets 404), which is
  outside this frontend repo's control.

## Structured data

- **Organization + WebSite** — rendered once, site-wide, via
  `GlobalSeo.jsx`. `WebSite` includes a `SearchAction` pointing at
  `/search?q={search_term_string}` (the app's real search route) so
  Google can offer a sitelinks search box.
- **BreadcrumbList** — built on product pages from the exact same items
  the visible `<Breadcrumb>` renders (`src/components/Product/
  useBreadcrumbItems.js`), so the structured data can never say something
  different from what's on the page.
- **Product** — name, description (plain text, HTML-stripped from the real
  sanitized product description), images, sku, category, and (when a real
  price exists) an `Offer` with real price/currency/availability/URL.

## Sitemap strategy

Product data lives in the backend database, not in this frontend's build
output — there's no way to enumerate "all products" at `vite build` time.
So the sitemap is generated by a **separate, opt-in script**, not baked
into `npm run build`:

```
VITE_SITE_URL=https://your-real-domain.com \
VITE_API_URL=https://your-api-domain.com \
npm run sitemap
```

This calls the same public `GET /api/products` endpoint the storefront
itself uses, paginates through every product, and writes
`public/sitemap.xml` with real product URLs and real `lastmod` dates (from
the API's `updatedAt`/`createdAt`). It also rewrites the `Sitemap:` line in
`public/robots.txt` to the same absolute site URL.

**Run this as a deploy step**, before `vite build`, so the generated
`sitemap.xml` gets copied into `dist/` along with the rest of `public/`.
It deliberately isn't wired into `build`/`build:analyze` directly — that
would make every local dev build silently require a reachable backend and
a configured `VITE_SITE_URL`.

## robots.txt

`public/robots.txt` is a real file now (it was previously an empty,
broken placeholder directory in this repo — same bug as the equally-empty
`public/manifest.json` directory, which is unrelated to SEO and left
untouched here). It disallows the same private/thin-content paths that are
also marked `noindex` in-page — the in-page `noindex` meta tag is what
actually matters for keeping those pages out of search results;
`robots.txt` is a courtesy that saves crawlers from requesting them in the
first place. Its `Sitemap:` line uses a `__SITE_URL__` placeholder that
`npm run sitemap` rewrites to the real origin — don't ship it with that
placeholder still in place.

## Environment

New optional variable: `VITE_SITE_URL` (see `.env.example`). Used to build
absolute canonical/OG URLs and by the sitemap script. Safe to leave unset
in development — `src/seo/siteConfig.js#getSiteUrl` falls back to
`window.location.origin` when it isn't configured.
